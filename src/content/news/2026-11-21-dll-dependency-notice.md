1.1.4 还在一轮轮改，测试的时候有人装完双击，弹出「计算机中丢失 libstdc++-6.dll」，程序没起来。

查下来是我们的问题，跟你的电脑无关。下面说清楚原因、你现在的处理办法，以及我们接下来怎么改。

## 原因：运行库没打进 exe

程序用 GCC（MinGW-w64）编译。默认情况下，C++ 标准库和运行时是外部依赖：exe 启动时去系统里找 `libstdc++-6.dll` 和 `libgcc_s_seh-1.dll`。这两个文件只在我装了开发工具的机器上有（MinGW 安装目录下，还被加进了 PATH），所以我这边双击就能跑。

你的电脑上没有这两个文件，Windows 在加载阶段就把程序拦下了，启动画面都出不来。

这里有个流传很广的说法要澄清：装「VC++ 运行库合集」不解决这个问题。`vcruntime140.dll`、`msvcp140.dll` 是微软编译器的运行库，跟 GCC 的这两个 DLL 不是一回事，装多少遍都没用。

这个疏漏从 1.0.0 就带着，一直到 1.1.3 都没被发现，因为我们测试用的机器上从来不缺这两个文件。

## 先看你的报错是哪一种

报错里的文件名不同，处理办法也不同。

**「丢失 libstdc++-6.dll」或「丢失 libgcc_s_seh-1.dll」**

这是我们的包缺运行库。下载页现在挂着的 1.0.0 ~ 1.1.3 全都是这个情况。两个办法：

- 等我们重编的包上线（下面「接下来会做的」第一条），换上就能开。
- 急着用：找一份 `libstdc++-6.dll` 和 `libgcc_s_seh-1.dll`，放进 `main.exe` 所在的文件夹，再双击。注意这两个文件要和编译时同一套 GCC，版本对不上可能还是报错，所以这只能当临时办法，不建议长期这么用。

**「丢失 api-ms-win-crt-runtime-l1-1-0.dll」这类**

这个不是我们带的东西，是 Windows 自带的 Universal C Runtime，按系统版本处理：

- Windows 10 / 11：系统自带，正常不会缺。真缺了把截图发给我们。
- Windows 7 SP1 / Windows 8.1：装 KB2999226（在 Windows Update 的可选更新里），装完重启。Win7 必须先有 SP1。
- Windows Vista / XP：微软没给这两个系统出 UCRT，程序不支持。

**「无法定位程序输入点 K32GetPerformanceInfo」**

系统低于 Windows 7。查内存用的那两个功能是 Win7 才加进系统的，Vista 上调不到，程序直接起不来，这个绕不过去。

## 最低需要什么系统

- Windows 10 / 11：双击就用，不用装任何东西。
- Windows 7 SP1 / Windows 8.1：先装 KB2999226。
- 低于 Windows 7：不支持。

## 已经改了什么

1.1.4 的编译参数加了 `-static -s`，把 GCC 的运行库静态链接进 `main.exe`。改完用 `objdump` 查了导入表，`libstdc++-6.dll` 和 `libgcc_s_seh-1.dll` 已经从依赖列表里消失。

代价是体积从 1 009 463 字节变成 1 729 536 字节，大了 0.69 MB。

## 接下来会做的

1. **安装说明补系统要求。** 写清 Win7 SP1 / 8.1 需要先装 KB2999226，别等人装完才发现打不开。
2. **发版前在干净系统上双击一次。** 以后上传前，先在一台没装 MinGW、没装任何运行库的机器或虚拟机上跑到主菜单，再发。
3. **Win7 真机验证一遍。** 目前关于 Win7 的结论都是静态分析出来的：控制台用 UTF-8（代码页 65001）在 Win7 上对中文支持不完整，可能出乱码或方块；启动链依赖的 PowerShell 在 Win7 上是 2.0 版本，语法支持但没实测。这两条要真机跑过才敢下结论。

另外说明一下为什么不能把 Universal C Runtime 也塞进 exe：MinGW-w64 的 UCRT 工具链不提供可静态链接的 UCRT，`ucrtbase.dll` 是系统级组件，微软不允许静态再分发。要做到零系统依赖，只能换 MSVCRT 工具链整体重编，那意味着另装一套编译器、19 个模块全部重测。这件事暂时不做，先把上面四件做扎实。

## 最后

一个打包环节就能解决的问题，拖到用户双击打不开才暴露。测试环境太干净，测不出这种错，这是我们的疏漏。
